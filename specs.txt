# Djezzy Resource Assignment Platform
## Database Specification and OpenCode Implementation Brief

**Version:** 1.0  
**Date:** 2026-08-10  
**Framework:** Laravel 13.x  
**Admin UI:** Filament 5.x  
**Database:** PostgreSQL recommended  
**Scope:** Database foundation before implementing the recommendation engine

---

## 1. Purpose

Build the complete data foundation for a company-wide platform that allows Djezzy to manage employees, organizational structure, skills, certifications, availability, workload, projects, and manual assignments.

The recommendation engine is intentionally postponed. The database must first support a complete manual workflow:

```text
Create organization structure
        -> Create employees and profiles
        -> Define skills and qualifications
        -> Track availability and workload
        -> Create projects and requirements
        -> Manually assign employees or teams
        -> Track assignment history
```

The design must support both IT and non-IT projects.

---

## 2. Implementation Strategy

Implement the system as a Laravel monolith with a modular domain structure. Do not create microservices for the first version.

Use:

- Laravel migrations for the database schema.
- Eloquent models for relationships and queries.
- Filament resources for administrative CRUD screens.
- Policies/permissions for authorization.
- Form Requests or Filament validation for input validation.
- Factories and seeders for realistic development data.
- PHPUnit/Pest tests for model relationships and business rules.

The recommendation engine must later be implemented as a separate application service. Do not place scoring logic inside migrations, models, Filament resources, or controllers.

---

## 3. Design Principles

1. Keep authentication separate from employee business data.
2. Do not store skills, languages, or certifications as comma-separated text.
3. Use many-to-many pivot tables for employee traits and project requirements.
4. Use foreign keys and unique constraints wherever appropriate.
5. Preserve business history; do not hard-delete employees, projects, or assignments casually.
6. Use soft deletes for entities that may be referenced by historical records.
7. Keep roles separate from organizational positions.
8. Allow one project to have one employee, multiple employees, a team, or a department.
9. Store dates and percentages for availability and workload instead of a single boolean `available` field.
10. Make the schema useful without the recommendation engine.

Laravel supports Eloquent one-to-many and many-to-many relationships through model relationship methods and pivot tables. [web:40] Laravel also provides soft-delete support through the `SoftDeletes` trait and a nullable `deleted_at` column. [web:47]

## 5. Core Table Definitions

The following definitions describe the required columns. All tables should include `created_at` and `updated_at` unless stated otherwise.

### 5.1 users

Use Laravel's default users table and add:

```text
id                 BIGINT primary key
name               VARCHAR
email              VARCHAR unique
password           VARCHAR
email_verified_at  TIMESTAMP nullable
is_active          BOOLEAN default true
last_login_at      TIMESTAMP nullable
remember_token     VARCHAR nullable
created_at         TIMESTAMP
updated_at         TIMESTAMP
```

The `users` table is for authentication and access control. It is not the employee profile table.

### 5.2 business_units

```text

updated_at         TIMESTAMP
```

Because `manager_id` references `employees`, add this foreign key only after the `employees` table exists, or add it in a later migration.

## 7. Foreign-Key Rules

Use these deletion behaviors:

- Organization parents: `restrict` or `no action` if historical data exists.
- Optional organization references: `nullOnDelete`.
- Employee profile linked to user: restrict or soft delete.
- Project references: restrict or soft delete.
- Child records such as employee skills: cascade when the employee is permanently deleted.
- Assignment history: never cascade-delete historical records accidentally.

The implementation agent must review every foreign key instead of applying `cascade` everywhere.

## 11. Validation Rules

Implement at application level and, where possible, database level:

- Employee code must be unique.
- Project code must be unique.
- Project target end date must be after or equal to the start date.
- Availability end date must be after or equal to the start date.
- Percentages must be between 0 and 100.
- Proficiency levels must be between 1 and 5.
- Ratings must be between 1 and 5.
- A project must have a valid category.
- A project must not be assigned to an inactive employee.
- An expired certification must not be treated as valid.
- A user may have multiple roles.
- A skill must not be duplicated for the same employee.
- A required skill must not be duplicated for the same project.

## 18. Final Architecture Decision

The recommended implementation path is:

```text
Laravel monolith
    + PostgreSQL
    + Eloquent
    + Filament admin panel
    + Role/permission package
    + PHPUnit or Pest tests
    + React later only for custom interfaces
```

The database and manual assignment workflow are the foundation. The recommendation system should be treated as a separate final module that consumes this foundation and produces explainable recommendations.
