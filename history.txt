================================================================================
PROJECT HISTORY — Djezzy Resource Assignment Platform
================================================================================
This file chronicles everything created for this project from start to now.
Stack: Laravel 13.24.0 · Filament v5.7.6 · PostgreSQL · Fortify · Spatie
Permission v8 · Inertia v3 + React · Playwright (Tier B browser QA). Test
suite: 124 tests / 492 assertions (PHPUnit) + 7 Playwright e2e specs.
Repository: git@github.com:Mohamed-Benkheira/BTS-rahmania.git.

--------------------------------------------------------------------------------
1. PROJECT ORIGIN
--------------------------------------------------------------------------------
The project is a resource assignment platform built against specs.txt. It lets
Djezzy manage employees, the organizational structure, skills, certifications,
languages, availability, workload, projects, and manual project assignments,
exposed through a Filament admin panel.

--------------------------------------------------------------------------------
2. MILESTONE 1 — DATABASE FOUNDATION
--------------------------------------------------------------------------------
- 39 database migrations covering the full spec:
  * Framework + auth tables (users, password reset tokens, sessions, jobs,
    cache, Fortify 2FA/passkeys).
  * Spatie RBAC (roles, permissions, model_has_roles, model_has_permissions).
  * Organization: business_units, departments, teams, positions, locations.
  * Employee domain: employees, employee_skills, employee_certifications,
    employee_languages, availability, workload, and ~30 employee tables total.
  * Projects: project_categories, projects, project_requirements,
    project_required_skills/certifications/languages.
  * Assignments: assignments, assignment_members, assignment_teams,
    assignment_status_history.
  * audit_logs.
  * Dormant recommendation tables (recommendations, recommendation_details,
    recommendation_eligibility, project_evaluations) — schema only, no logic.
- Circular foreign keys between department/team/employee managers resolved in a
  follow-up migration (managers nullable + FK added after tables exist).
- Database-level CHECK constraints: proficiency 1-5, percentages 0-100,
  start-before-end dates, ratings 1-5.
- 26+ unique constraints to prevent duplicates.
- Soft deletes on Employee, Project, and Skill.
- Data integrity guarantees added later (see section 7):
  * Partial unique index `assignments_single_current` — at most one
    approved/active assignment per project; historical records still allowed.
  * `employees.user_id` FK uses restrictOnDelete — a linked user account cannot
    be deleted while an employee profile references it.
- 30 Eloquent models with all spec'd relationships: employee skills/certs/
  languages, availabilities, workloads, assignments; project requirements +
  required skills/certs/languages; assignment members/teams/status history.
- 18 model factories + 6 seeders producing realistic fictional data:
  4 business units, 9 departments, 8 teams, 12 positions, 5 locations,
  30 employees, 40 skills, 10 certifications, 8 languages, 10 project
  categories, 10 projects (5 of which are manually assigned).

12. MILESTONE 4 — RECOMMENDATION ENGINE
--------------------------------------------------------------------------------
- RecommendationService (app/Services/RecommendationService.php): generates
  ranked candidate recommendations for a project based on its assignment_mode:
  * single_employee / multiple_employees -> ranks eligible ACTIVE employees not
    already assigned to the project (approved/active assignments).
  * team -> ranks teams that have at least one active employee and are not
    already assigned, using the team's COLLECTIVE skills/certs/languages as well
    as average availability and workload across active members.
  * department -> ranks departments (any with active employees) using collective
    capabilities and averages computed across all active department employees.
- Weighted scoring (defaults): skills 40%, certifications 20%, languages 15%,
  availability 15%, workload 10%. Weights for absent requirement categories are
  dropped and the remainder renormalized. Custom weights injectable via
  `weights()`.
- Each run stores: algorithm version, criteria snapshot (project id,
  assignment_mode, requirement counts, weights), executed_at; rankings are saved
  as Recommendation rows with employee_id XOR team_id XOR department_id (only
  the target matching the project mode is populated), rank, total_score,
  explanation (per-component breakdown incl. team_size / department_size), and
  status (pending/approved/rejected). Audit log entry 'recommendation.run' is
  written for every run.
- Filament integration:
  * EditProject header action "Recommend" runs the engine via confirmation modal
    and notifies with count + top pick (name resolves to employee/team/
    department depending on mode).
  * RecommendationsRelationManager on ProjectResource shows run history (run #,
    executor, algorithm, assignment mode badge, candidate count, executed at)
    with a "View Rankings" modal rendering the ranked list + score breakdown.
  * resources/views/filament/admin/recommendations-modal.blade.php renders each
    ranked target with score %, status badge, and per-component breakdown.
- RecommendationPolicy + ProjectEvaluationPolicy created and registered in
  AppServiceProvider.
- ProjectEvaluation full CRUD resource added under
  app/Filament/Admin/Resources/ProjectEvaluations (schema existed).
- Notifications table migration added (standard Laravel schema) so Filament
  notifications persist.
- RolesAndPermissionsSeeder extended to 62 permissions; 8 M4-related permissions
  granted to admin/project-manager (run + approve recommendations, evaluations)
  and hr (view/create evaluations).
- Tests: 9 new RecommendationServiceTest cases incl. team-mode and
  department-mode ranking + eligibility exclusions. Suite now 85 tests / 357
  assertions — all green.
- Note: Assignments intentionally remain a manual, human-audited step; the
  engine recommends, managers decide.

14. MILESTONE 5 — ENGINE HARDENING + CLOSING THE RECOMMENDATION→ASSIGNMENT LOOP
--------------------------------------------------------------------------------
- RecommendationService hardened (algorithm 1.1.0):
  * Expired-certification bug fixed: scoring now uses
    EmployeeCertification::isCurrentlyValid() (Verified + not expired) in
    scoreCertificationsFromCollection and in team/department aggregation; an
    expired cert no longer counts toward a match and can no longer satisfy a
    mandatory certification requirement (spec §11).
  * Mandatory-requirement gating: scoreEmployee/Team/Department return null when
    a mandatory requirement is unmet and are dropped from rankings. New
    mandatoryRequirementReason() flags missing mandatory skills, proficiency
    below required minimum, expired/absent mandatory certifications, and
    language below the required minimum level.
  * Availability-missing policy: candidates with no current availability record
    now get DEFAULT_AVAILABILITY_SCORE (0.5) instead of a free default of 1.0.
  * Audit payload now records eligible_count + excluded_by_mandatory.
- 6 new test cases (expired cert ignored for scoring and for mandatory gating,
  mandatory skill + below-minimum gating, neutral availability score, audit
  exclusion count). Three existing tests updated to non-mandatory requirements
  so both candidates stay eligible.
- Closing the loop — assignments:
  * AssignmentsRelationManager added to ProjectResource (type/status badges,
    member count, dates, assigner, approved-at, status + type filters).
  * EditProject "Create Assignment" header action (prefilled start/end dates +
    notes) creates a pending assignment through AssignmentService and notifies;
    blocks with a danger toast when the project already has an approved/active
    assignment.
  * RecommendationsRelationManager "Create Assignment from Top Match" action:
    approves the rank-1 pending recommendation, creates the assignment, attaches
    the employee / team / all active department employees, and audits the
    approval. Guarded by the same no-current-assignment rule.
- Tier B Playwright browser QA (previously deferred):
  * @playwright/test + chromium; playwright.config.ts with webServer
    (reuseExistingServer), global setup that logs in once and shares the session
    via storageState, workers=1 for the single-threaded dev server.
  * tests/e2e/assignments-flow.spec.ts: login reaches admin panel, Assignments
    manager + Create Assignment flow end-to-end, rankings modal renders in light
    + dark (screenshots artifacts/rankings-light.png/dark.png), and the
    Create-Assignment-from-Top-Match action is present.
  * App\Console\Commands\EnsureE2EProject provides a fixture project without a
    current assignment so the assignment-creation flow is always testable.
- Fortify login rate limiter left at 5/min (business behavior); the full rate
  limit test continues to pass. Login rate-limiting behavior verified in the
  test suite only.
- Test suite now 93 tests / 376 assertions (PHPUnit) + 5 Playwright e2e — all green.
- Zero-candidate diagnosis & demo-data guarantee:
  * Reported behavior: the engine returned 0 candidates for every project
    because strict mandatory gating correctly excluded everyone while the
    seeded requirements were unsatisfiable (e.g. Docker @5 on Mobile App
    Redesign, Terraform @3 on 5G Core Rollout).
  * Recommendation runs now record mandatory "blockers" (recommendation_runs.
    blockers, JSON): when a run yields no candidates, RecommendationService
    computes the distinct unmet mandatory requirements across the active
    workforce and stores them on the run + audit payload.
  * EditProject "Recommend" now surfaces a danger+persistent notification
    listing each unresolved requirement instead of a bare "0 recommendations".
  * RecommendationsRelationManager gained a red "Blockers" column (count badge
    + tooltip with the reasons) and the View Rankings modal shows the blocker
    list in its empty state.
  * Seed data made deterministically satisfiable: every employee gets all
    skills at proficiency >= 4, every core certification verified, and every
    language (Arabic native, all others advanced); required skill minimum
    proficiency is capped at 4; core cert + full language pools are used as
    requirement sources. A regression test (SeedDataProducesRecommendationsTest)
    seeds the full database and asserts every project yields >= 1 candidate
    with no blockers.
- Test suite now 96 tests / 406 assertions (PHPUnit) + 5 Playwright e2e — all green.

15. MILESTONE 6 — EMPLOYEE SELF-SERVICE PORTAL (+ APPROVAL WORKFLOW + NOTIFICATIONS)
--------------------------------------------------------------------------------
Overview: employees now get a self-service React portal at /portal/* to update
their own skill/language/certification/availability/profile data. Every change
is a request that HR (or an admin as fallback) approves inside Filament, and
in-app (database) notifications keep reviewers and employees in sync via an
admin bell and an employee bell.

Workflow & permission gate:
  * Two new permissions: "view profile change requests" + "approve profile
    change requests" (added to RolesAndPermissionsSeeder for super-admin, admin,
    and hr; seeder re-run on the dev DB). ProfileChangeRequestService::canReview
    = user->can('approve profile change requests'); HR approves every change,
    admins/super-admin act as fallback.
  * Requests are stored in profile_change_requests (employee FK restrict,
    type enum profile|skill|language|certification|availability, subject_id,
    payload JSON, previous JSON, status pending|approved|rejected, submitted_note,
    reviewer_id/note, reviewed_at). Approval applies the change immediately; the
    "previous" snapshot is kept for audit.
  * Per-type business rules on approval: profile fields phone/biography/
    profile_photo_path/birth_date are overwritten; skills attached/updated with
    verified_at + verified_by; certifications attached/updated with
    verification_status=verified and document kept; languages get speaking/
    writing/reading levels; availability inserts a new record (latest start date
    wins, no overlap blocking; status inferred from the percentage: 0 => on leave,
    <100 => partially available, full => available).
  * Domain exceptions guard double-review and unauthorized review; audit actions:
    profile-change.requested / approved / rejected.

Notifications & bell:
  * DB-channel notifications: ProfileChangeRequested (to HR+admin on submit),
    ProfileChangeResolved (to the employee on approve/reject), plus the existing
    AssignmentCreated (reviewers) and AssignmentStatusChanged (members);
    CertificationNearExpiry ran by `php artisan notification:certifications-near-expiry`
    (default --days=60) for verified certs expiring within the window.
  * App\Services\NotificationService (toReviewers / toUsers) is resilient when
    roles are not yet seeded. Admin panel enables filament()->databaseNotifications()
    + 30s polling; the employee portal renders a bell (NotificationBell) polling
    unread-count/recent JSON every 30s with a dropdown + mark-all-read.

Portal backend & frontend:
  * EnsureEmployeeProfile middleware gates /portal/* to authenticated users with a
    linked employee profile + employee role (403 JSON for APIs, redirect home
    otherwise). Routes under routes/portal.php, names portal.*, no verified-mail
    requirement since HR-created accounts may be unverified.
  * Portal controllers: dashboard (stats, current assignment, latest availability),
    profile, skills, languages, certifications (document upload to the
    certification-documents public disk), availability, requests, assignments,
    evaluations, notifications (unread-count + recent JSON).
  * Shared Inertia props extended: auth.roles, auth.employee, notifications.
    unread_count, flash.toast. Controllers flash via Inertia::flash('toast',...)
    matching the existing useFlashToast hook.
  * React portal: own PortalLayout + PortalSidebar (10 nav items), 10 pages under
    resources/js/pages/portal/*, wireframes consistent with the admin design
    language, wayfinder helpers regenerated with .form() variants.
  * Evaluations page fixed to the real project_evaluations schema (rating,
    communication/delivery/quality ratings, comments, evaluated_at).

Filament review resource:
  * ProfileChangeRequests resource (Employees group, nav sort 6): list + view
    only (no create). Table: employee, type badge, subject (subjectDisplay()),
    status badge, submitted (default sort desc), reviewed-by; type/status select
    filters; employee cell links straight to the view page. View page infolist
    shows employee/type/subject/status/note/reviewer plus KeyValueEntry
    "Proposed changes" and (when present) "Previous state", with header
    Approve/Reject modal actions (reviewer note optional) that resolve the
    request, audit, notify, and refresh the form state.

Fixes made while wiring tests:
  * notifications.data converted json -> jsonb (new migration + USING cast) —
    Filament's databaseNotifications() query (data->>'format') requires jsonb on
    PostgreSQL.
  * NotificationService::toReviewers no longer throws when roles are missing.
  * ProfileChangeRequestService::snapshot now receives $payload (was undefined).
  * ProfileChangeRequestsTable: defaultSort moved to the table (not the column);
    subjectDisplay() exposed via ->state() callback (method, not an attribute);
    resource no longer sets recordTitleAttribute to the type enum.
  * Infolist Section imported from Filament\Schemas\Components.
  * Modal Approve/Reject submit labels set explicitly.
  * Double-toast bug fixed: useFlashToast removed from PortalLayout (the global
    sonner Toaster already subscribes and was rendering duplicate toasts).
  * EvaluationsController referenced a non-existent column set; rewired to the
    real schema and the portal page updated.

Tests:
  * New PHPUnit: ProfileChangeRequestServiceTest (submit snapshot + validation per
    type, approve applies profile/skill/cert/language/availability correctly incl.
    verified pivots, reject leaves data untouched, permission + double-review
    guards, audit rows, reviewer/employee notifications),
    NotificationServiceTest (role targeting, actor exclusion, missing-role
    resilience), PortalAccessTest (middleware for employee/admin/absence,
    page render loop, profile submit, skill validation, unread-count JSON).
  * New Playwright e2e (portal-profile-flow.spec.ts + App\Console\Commands\
    EnsureE2EEmployee fixture): employee logs into /portal, submits a language
    change, HR/super-admin approves it in /admin/profile-change-requests, and the
    employee sees the Approved badge + unread bell; a second spec verifies a
    pending profile request lands in the admin table.
  * Baselines fixed while wiring: AssignmentServiceTest suite needed the new test
    suite counts (role resilience) to stay green.
- Test suite now 119 tests / 481 assertions (PHPUnit) + 7 Playwright e2e — all green.

  redirects post-login straight to the user's defaultPath() (with intended())
  and uses Inertia::location() so the login POST (an X-Inertia request) can
  navigate to the non-Inertia Filament panel (for non-Inertia requests it falls
  back to a normal redirect). Location logic shared via App\Models\User::
  defaultPath(). Without the X-Inertia-Location (409) signal the Inertia client
  swallowed the admin redirect and the browser stayed on /login.
- Tests: new RootRedirectTest (guest->login, employee->portal,
  employee-without-profile->dashboard, admin->/admin, no-role->/admin);
